# Actor 建模

## 按串行化需求选择 Actor

当同一标识的命令必须串行处理、状态存在生命周期或故障需要隔离时，才适合使用 Actor。常见标识包括玩家、队伍、房间、对局、场景分区、公会和分片协调器；不可变数据与纯无状态函数不需要 Actor。

## 状态放置

- 玩家 Actor：玩家自身成长与编排，不承载全部共享子系统。
- 场景/格子 Actor：该分区的空间状态与视野管理。
- 战斗 Actor：具有受限生命周期、按输入顺序处理的对局状态。
- 公会 Actor：公会范围变更；高频聊天和在线状态应与持久成员拆分。
- 协调 Actor：租约、路由或拓扑决策；不得处于批量数据主路径。

## 生命周期

定义激活来源、重复激活防护、空闲超时、钝化、优雅排水、快照/刷盘点、崩溃恢复和过期消息拒绝。旧实例可能继续发送命令时，必须使用 epoch/fencing token。

## 消息设计

- 命令表达意图，所有可重试变更都携带唯一操作 ID。
- 查询必须有 deadline，不能包含隐式持久化变更。
- 事件表示事实，具有稳定 ID 与 schema 版本。
- 将顺序键放入路由决策，默认不承诺全局顺序。
- 限制 payload 与邮箱增长；大对象适用时传递存储引用或通过流式适配层传输。

## 避免

- 没有生命周期或串行化理由时，为每个数据库行创建 Actor。
- 跨多个服务的 Actor 同步 Call 链。
- 等待远程 Actor 时长时间占用数据库事务。
- 在回调中创建 goroutine 以绕过邮箱顺序。
- 重启 Actor 后假定易失内存已自动恢复。
